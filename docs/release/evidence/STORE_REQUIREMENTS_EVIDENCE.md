# Store & regulatory requirements — research evidence (verified 2026-10-14)

Produced by a multi-agent research run that fetched official sources (developer.apple.com, developer.android.com, support.google.com/googleplay, docs.expo.dev, Egyptian government and other reputable sources). Each finding carries its confidence level. **Only `verified-official` findings are treated as requirements**; the rest are leads to confirm. Raw data: `store-requirements-2026-10-14.json`.

## apple-build

_apple-build: Apple build and submission technical requirements as of 2026-10-14 (Xcode/SDK minimums, deployment target, screenshots, app icon, Universal Links, TestFlight, export compliance), checked against Expo SDK 57 / RN 0.86_

- **[verified-official]** Current upload minimum: since April 28, 2026, every build uploaded to App Store Connect must be built with Xcode 26 or later using the iOS 26 SDK (or the matching iPadOS/tvOS/visionOS/watchOS 26 SDK). The user's claim of 'Xcode 26 / SDK 26' is correct. — effective 2026-04-28  
  Source: https://developer.apple.com/news/upcoming-requirements/  
  Implication: Build with Xcode 26.x. Expo SDK 57 needs Xcode 26.4+ anyway, so meeting Expo's minimum also meets Apple's. Add a CI release check that fails if the Xcode/SDK major version is below 26.
- **[verified-official]** Next upload minimum, starting April 2027 (Apple gives the month only): iOS/iPadOS apps must be built with the iOS & iPadOS 27 SDK or later and must target iOS 15 or later. Xcode 27 (27A266a) shipped on September 14, 2026, and Xcode 27.1 RC (27A9275) on October 5, 2026. — effective April 2027 (exact day not published)  
  Source: https://developer.apple.com/app-store/submitting/  
  Implication: Xcode 27 is not required today. Plan to move to an Expo SDK and EAS image that build with Xcode 27 before April 2027. Expo's EAS image list already has an Xcode 27.0 image tagged sdk-58. Apple's Sept 9, 2026 news post (https://developer.apple.com/news/?id=k1mtkt1k) confirms the SDK-27 rule.
- **[verified-official]** Minimum deployment target: since September 9, 2026, iOS and iPadOS apps uploaded to App Store Connect must target iOS 13 or later. — effective 2026-09-09  
  Source: https://developer.apple.com/news/upcoming-requirements/  
  Implication: Expo SDK 57's floor of iOS 16.4 already satisfies both this rule and the April 2027 iOS 15 floor. Do not set ios.deploymentTarget below 16.4. Any value from 16.4 upward is compliant.
- **[verified-official]** Expo SDK 57 platform table: React Native 0.86, React 19.2.3, Node 22.13.x minimum, Android 7+, compileSdk/targetSdk 36, iOS 16.4+, Xcode 26.4+.  
  Source: https://docs.expo.dev/versions/latest/  
  Implication: Confirms the project stack (SDK 57 + RN 0.86). For iOS, use deployment target 16.4 or higher and Xcode 26.4 or later. The latest docs page is SDK 57 ('Reference (v57.0.0)').
- **[verified-official]** On EAS Build, the iOS image tagged for SDK 57 (also currently 'latest') is macos-tahoe-26.5-xcode-26.6, which ships Xcode 26.6 (17F113). Separate images exist for Xcode 27.0 (tagged sdk-58) and Xcode 27.1 RC.  
  Source: https://docs.expo.dev/build-reference/infrastructure/  
  Implication: Pin ios.image in eas.json to 'sdk-57' or 'macos-tahoe-26.5-xcode-26.6' so builds are reproducible and meet the Xcode 26 rule. Don't switch to Xcode 27 images until Expo confirms SDK 57 supports them.
- **[official-but-ambiguous]** Screenshot basics: at least 1 and up to 10 screenshots per device size, in .jpeg/.jpg/.png. Required sets: iPhone needs at least one for 'iPhone with Dynamic Island (medium display)'. iPad needs at least one for the 13-inch display, but only if the app supports iPadOS. Screenshots can't include alpha channels or transparency. Apple's page now names device classes, not 6.9"/6.5". Accepted sizes: Dynamic Island medium display 1206x2622 or 1179x2556. Dynamic Island large display (the 6.9" class) 1320x2868, 1290x2796 or 1260x2736. Face ID large display (the 6.5" class) 1284x2778 or 1242x2688.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications  
  Implication: Apple's page contradicts itself. The header requires the medium-display set, but the Face ID (large display) card says 'Required if app runs on iPhone and screenshots for iPhone with Dynamic Island (large display) aren't provided'. To be safe, prepare portrait sets at 1206x2622 (medium) and 1320x2868 (large), flattened PNG/JPEG with no alpha, for both the Arabic and English localizations. The user's '6.9"/6.5"' labels are outdated.
- **[verified-official]** iPad screenshots (13-inch: 2064x2752 or 2048x2732 portrait) are required only if the app runs on iPad natively. In Expo, ios.supportsTablet defaults to false. App Review Guideline 2.4.1 encourages iPad support but does not require it.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/screenshot-specifications  
  Implication: Decide on ios.supportsTablet deliberately. Leaving it false (the Expo default) avoids the iPad screenshot requirement and iPad layout review. Setting it true means 13-inch iPad screenshots plus iPad-responsive and RTL layouts. Guideline 2.4.1 (https://developer.apple.com/app-store/review/guidelines/) says: 'iPhone apps should run on iPad whenever possible.'
- **[official-but-ambiguous]** iPhone Duo (on sale October 23, 2026) has screenshot sizes of 1398x2034 for the outer display and 2007x2853 for the inner display. Apple says iPhone Duo screenshots become required in April 2027, but its two statements describe the trigger differently. — effective April 2027  
  Source: https://developer.apple.com/news/?id=kkphp5qo  
  Implication: Not needed for a 2026 launch on Xcode 26. Add a backlog item to make Duo-responsive layouts and Duo screenshots alongside the Xcode 27 / iOS 27 SDK migration before April 2027.
- **[verified-official]** App Review Guideline 2.3.3: screenshots must mostly show the app in use. Review approves only submissions where more than half of each device's screenshots show the app in use. Screens that only show login or splash are not acceptable.  
  Source: https://developer.apple.com/help/app-review/guideline-reference/2-3-3-screenshots  
  Implication: Most screenshots should show real Patient/Doctor/Nurse flows (wound tracking, booking, TetraSol store, AI assistant). Use synthetic, non-identifiable patient data and wound images. Marketing frames must stay a minority.
- **[verified-official]** App icon spec: on iOS/iPadOS the icon is a square 1024x1024 px layered design. The system masks it to a rounded rectangle and supports default, dark, clear and tinted appearances. Xcode can generate every size from one 1024x1024 image, or icons can be authored in Icon Composer. Any imported background layer must be full-bleed and opaque.  
  Source: https://developer.apple.com/design/human-interface-guidelines/app-icons  
  Implication: Supply a square 1024x1024 sRGB/P3 master with no pre-rounded corners. Expo's ios.icon accepts a PNG path, a {light, dark, tinted} object, or an Icon Composer '.icon' directory, and says to 'Use a 1024x1024 icon which follows Apple's interface guidelines for icons, including color profile and transparency' (https://docs.expo.dev/versions/latest/config/app/).
- **[secondary-source-only]** The rule that the 1024x1024 App Store icon must have no alpha channel is enforced at upload (error ITMS-90717 'Invalid large app icon'). It is documented only by developer reports, not on any Apple page fetched today.  
  Source: https://developer.apple.com/forums/thread/795411  
  Implication: Flatten the light/default iOS icon PNG onto the brand background with no alpha before building, and add a CI check (e.g. `sips -g hasAlpha` or ImageMagick) that fails if it has alpha. The only exception: Apple's Xcode doc says the dark variant should have a transparent background.
- **[verified-official]** Universal Links basics: (1) Host a file named exactly 'apple-app-site-association' (no extension) at https://<fully qualified domain>/.well-known/apple-app-site-association. (2) Serve it over HTTPS with a valid certificate and no redirects. (3) Each subdomain needs its own file and its own entitlement entry. (4) Entitlement format is <service>:<fully qualified domain>, e.g. applinks:example.com. (5) appIDs use the form <TeamID>.<BundleID>. (6) Since iOS 14, devices fetch the file through Apple's CDN, which requests it within 24 hours; devices recheck about weekly.  
  Source: https://developer.apple.com/documentation/xcode/supporting-associated-domains  
  Implication: Set ios.associatedDomains, e.g. ['applinks:<domain>'] (no https:// prefix), with one entry per subdomain and per bundle-ID variant (dev/staging/prod). Use Apple's current 'appIDs' + 'components' AASA format; Expo's docs example still uses the older 'appID'/'paths' keys. Paymob payment-return URLs need their own explicit, excluded or included path rules.
- **[verified-official]** Apple warns that Universal Links are an attack vector. Apps must validate every URL parameter, discard malformed URLs, and must not let a link directly delete content or expose sensitive user information.  
  Source: https://developer.apple.com/documentation/xcode/supporting-universal-links-in-your-app  
  Implication: Deep links to wound records, consultations, orders or Paymob results must be schema-validated in Expo Router, must require authentication and a role check (patient/doctor/nurse) before showing PHI, and must never trigger destructive or payment actions on their own.
- **[verified-official]** TestFlight basics: up to 100 internal testers and 10,000 external testers. A build is testable for up to 90 days. Adding the first build to an external group sends it to TestFlight App Review, which approves before testing starts. An internal group must exist before an external group can be created. Up to six builds can go to TestFlight review in 24 hours, with one build per version in review at a time. A Beta App Description and Feedback Email are required for external testing.  
  Source: https://developer.apple.com/help/app-store-connect/test-a-beta-version/invite-external-testers  
  Implication: Release runbook: upload, then internal group (team), then external groups (e.g. pilot doctors/nurses). Provide the Beta App Description (required field per /provide-test-information) and a feedback email, plus 'What to Test' notes. Keep production Paymob keys out of TestFlight builds, or flag them clearly.
- **[verified-official]** Beta App Review details: contact name, email and phone; a demoAccountRequired flag with demo username and password; notes up to 4,000 characters. The API docs say: 'Credentials must be valid and active for duration of review.' For App Store review, the demo account 'must not expire', and the contact phone must be in international format with '+' (App Store Connect help, reference/app-review-information).  
  Source: https://developer.apple.com/documentation/appstoreconnectapi/betaappreviewdetail/attributes-data.dictionary  
  Implication: Create permanent review accounts for Patient, Doctor and Nurse, pre-verified and not blocked by OTP or license checks. Put the extra roles' credentials in Notes with clear steps. Use an Egyptian contact phone in +20 format. Keep backend and Paymob sandbox live during review.
- **[verified-official]** Export compliance: setting ITSAppUsesNonExemptEncryption=NO in Info.plist declares no encryption or only exempt encryption (Apple gives OS-provided HTTPS via URLSession as typically exempt). YES means non-exempt encryption and usually needs ITSEncryptionExportComplianceCode from Apple's documentation review. Without the key, App Store Connect asks the questionnaire on every upload, and TestFlight builds show 'Missing Compliance' until it is answered. Apps using exempt encryption may still have to file a year-end self-classification report with the US government.  
  Source: https://developer.apple.com/documentation/security/complying-with-encryption-export-regulations  
  Implication: In Expo, set ios.config.usesNonExemptEncryption (it writes ITSAppUsesNonExemptEncryption). If the app only uses HTTPS/TLS and OS crypto (Keychain via expo-secure-store, platform crypto), false is likely correct, but the developer is legally responsible for the call. Add any custom or E2E crypto library (e.g. for chat or records) to the review first. Also see https://developer.apple.com/documentation/bundleresources/information-property-list/itsappusesnonexemptencryption.
- **[verified-official]** Regulated medical device declaration: apps available in the EU/EEA, UK or US must declare whether they are regulated medical devices in App Store Connect if either (a) their primary or secondary category is Health & Fitness or Medical, or (b) they answered 'frequent' to Medical or Treatment Information in the age rating questionnaire. Declaring 'Yes' requires an SRN or FDA number, an instructions-for-use URL, a use statement and safety information.  
  Source: https://developer.apple.com/help/app-store-connect/manage-app-information/declare-regulated-medical-device-status  
  Implication: If distribution is Egypt-only, this section does not apply as written. If the Medical/Health category is used and the app is also offered in EU/UK/US, answer it, most likely 'No' unless the AI wound features amount to diagnosis or treatment needing CE/UKCA/FDA authorization. Keep store availability limited to Egypt until this is decided.
- **[verified-official]** Privacy-manifest gate on upload: since May 1, 2024, new or updated apps must include approved reasons for the listed 'required reason' APIs, including APIs used by third-party SDKs. — effective 2024-05-01  
  Source: https://developer.apple.com/news/upcoming-requirements/  
  Implication: Check that the generated PrivacyInfo.xcprivacy covers app code plus all native modules (Expo modules, Paymob SDK, analytics/crash SDKs). Add any missing reasons via ios.privacyManifests in app.config.ts.
- **[verified-official]** Age rating questionnaire: updated questions were due by January 31, 2026, to avoid blocked submissions. Questions about social media capabilities were added on July 9, 2026, and answers are required for new submissions and updates from September 2026. — effective 2026-01-31 / September 2026  
  Source: https://developer.apple.com/news/?id=tlur8uvi  
  Implication: Complete the full questionnaire, including Medical/Treatment Information and social-media capability. Doctor/patient messaging is likely not a social feed, but answer deliberately. Note that 'frequent' medical information triggers the medical-device declaration for EU/UK/US storefronts.
- **[official-but-ambiguous]** An updated Apple Developer Program License Agreement was published on October 13, 2026, and the account holder needs to sign in and accept it. — effective 2026-10-13  
  Source: https://developer.apple.com/news/?id=17mwd36z  
  Implication: The account holder should accept the new agreement in the developer account before the first upload or submission. The news post does not say whether uploads are blocked until accepted; it only asks for acceptance.

## apple-privacy

_apple-privacy: App Privacy labels, PrivacyInfo.xcprivacy / Required Reason APIs, third-party SDK manifests and signatures, Guideline 5.1.1 (account deletion, permissions, purpose strings), 4.8 Login Services / Sign in with Apple, ATT. Verified 2026-10-14. The App Review Guidelines page reads "Last Updated: June 8, 2026"._

- **[verified-official]** The App Review Guidelines in force today were last updated on June 8, 2026. Every guideline quote below comes from that version. — effective 2026-06-08  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Cite this version in the compliance docs. Check the guidelines again before each submission.
- **[verified-official]** Guideline 4.8 applies only when a third-party or social login (Facebook, Google, X, LinkedIn, Amazon, WeChat and similar) sets up or authenticates the user's primary account. In that case the app must also offer an equivalent login service that limits data collection to name and email, lets the user keep their email private, and does not collect interactions for advertising without consent. No other login service is needed when the app uses only the company's own account system. Since the 2024 rewording, the guideline no longer names Sign in with Apple specifically.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Sign in with Apple is NOT required. The app only uses its own email/password and phone OTP, both through Better Auth, its own backend. Do not add the expo-apple-authentication plugin or the entitlement. If Google, Facebook or any other social login is added later for any role, 4.8 starts to apply, and Sign in with Apple becomes the practical way to comply. Keep a regression check on this.
- **[verified-official]** Guideline 5.1.1(v): an app that supports account creation must let users delete their account from inside the app. An app without significant account-based features must work without a login. Apps may not require personal information unless it is directly relevant to the core functionality or required by law. Apple's news post set the enforcement date as June 30, 2022. — effective 2022-06-30 (per https://developer.apple.com/news/?id=12m75xbj)  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: All three roles (Patient, Doctor, Nurse) need an easy-to-find in-app 'Delete account' entry under Account/Settings. It must delete the account, not just deactivate it. Personal data should be requested only where it is needed. Consider letting guests browse public content, such as the TetraSol catalog or education pages, without logging in. This is recommended, not mandatory, because the app has significant account-based features.
- **[verified-official]** Apple's account-deletion support page sets these rules. The option must be easy to find, typically in account settings. The app must offer to delete the entire account record and associated personal data; deactivation alone is insufficient. A link straight to a web deletion page is allowed. Apps in highly regulated industries under 5.1.1(ix) may add customer-service flows to confirm deletion, while other apps must not require calls, emails or chat. A confirmation step is fine. Manual deletion that takes time is acceptable if the user is told how long it will take and gets a confirmation when it is done. Users with an auto-renewable subscription must be told that billing continues through Apple. Deletion can be scheduled for the subscription's expiry only if an immediate-deletion option also exists.  
  Source: https://developer.apple.com/support/offering-account-deletion-in-your-app/  
  Implication: Build an in-app deletion flow: confirmation, a stated timeline, then a completion notice. As healthcare, the app may add a verification or customer-service step, but it must not make deletion unnecessarily hard. Where Egyptian law requires keeping medical or transaction records, document what is retained and why; local law was not verified here. If Silver/Gold/Platinum are sold as auto-renewable IAP subscriptions, the deletion flow must warn that Apple billing continues and tell the user to cancel. Sign in with Apple token revocation does not apply because Sign in with Apple is not used.
- **[verified-official]** Guideline 5.1.1(i): every app must link its privacy policy both in the App Store Connect metadata field and inside the app, in an easily accessible place. The policy must say what data is collected, how, and all of its uses. It must confirm that third parties (analytics, SDKs and others) give equal protection. It must explain retention and deletion and how to revoke consent or request deletion.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Publish Arabic and English privacy policies covering wound photos and health data, AI assistant processing, Paymob payments, doctor and nurse matching, retention and deletion. Link the policy in App Store Connect and from a Privacy Center screen in the app.
- **[verified-official]** Guidelines 5.1.1(ii) to (iv), on permission, data minimization and access. Apps must get consent before collecting user or usage data. Paid functionality must not depend on granting data access. Users need an easy way to withdraw consent. Purpose strings must clearly and completely describe the use. Apps should request only data relevant to core functionality, preferring out-of-process pickers over full Photos or Contacts access. Apps must not manipulate or force consent to unnecessary access, and should offer alternatives, such as manual address entry when Location is declined.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Request camera and photos only at the moment a wound photo is taken. Prefer the system photo picker (PHPicker, as used by expo-image-picker) over full library access. Request location only for nurse or home-visit matching, and offer manual address entry when it is declined. Silver/Gold/Platinum benefits must not depend on granting location, notifications or tracking. Do not add permissions for features that are not shipped, such as microphone or contacts.
- **[verified-official]** Purpose-string rules from Apple's 'Requesting access to protected resources' page. A string must not be blank. It must be under 4,000 bytes. It must accurately and specifically explain why access is needed, and these rules apply to localized strings too. App Review rejects binaries whose code references a protected API without the matching key (ITMS-90683). Accessing a resource without the string fails and may crash the app. Localize each string for every locale the app supports.  
  Source: https://developer.apple.com/documentation/uikit/requesting-access-to-protected-resources  
  Implication: Set specific Arabic and English strings (NSCameraUsageDescription, NSPhotoLibraryUsageDescription and NSLocationWhenInUseUsageDescription if used) through the Expo plugin options or ios.infoPlist. Add Arabic translations through the Expo 'locales' map ({"ar": "./languages/ar.json"} with an ios.NS*UsageDescription key in each file). The current apps/mobile/app.json already sets CFBundleAllowMixedLocalizations=true, as Expo requires. Remove permission plugins for unused features so their API references and keys do not ship.
- **[verified-official]** Expo localizes iOS permission messages per locale. Set ios.infoPlist.CFBundleAllowMixedLocalizations: true and point 'locales' at JSON files whose 'ios' object holds the usage-description keys. Prebuild writes these values into each locale's InfoPlist.strings.  
  Source: https://docs.expo.dev/guides/localization/  
  Implication: Add apps/mobile/languages/ar.json and en.json with CFBundleDisplayName ('غير لي' / 'Dress My Wound') and every NS*UsageDescription key. Register them under expo.locales.
- **[verified-official]** Guideline 5.1.1(ix): apps that provide services in highly regulated fields, including healthcare, should be submitted by a legal entity that provides the services, not by an individual developer.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Enroll in the Apple Developer Program as an organization, the Egyptian company that provides or contracts the healthcare services. An individual account is likely to be rejected. The seller name shown should match that entity.
- **[verified-official]** Guideline 5.1.2(i), current text: personal data may not be used, sent or shared without permission. Sharing with third parties, explicitly including third-party AI, must be clearly disclosed and explicitly permitted first. Tracking requires App Tracking Transparency permission. Apps may not require users to enable push, location or tracking to access functionality or receive compensation. — effective Text present in the June 8, 2026 version. Secondary sources say the AI wording was added on Nov 13, 2025.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: If the AI assistant sends user messages, wound photos or health data to an external model provider, show a clear disclosure naming the provider type and data and get an explicit opt-in before first use, with a way to withdraw. Without consent, AI features must stay off. Subscription tiers must not require enabling push notifications or location.
- **[official-but-ambiguous]** Guideline 5.1.3 on health data. Health, fitness and medical data may not be used or disclosed for advertising, marketing or data mining, except to improve health management or for health research, and then only with permission. The specific health data collected from the device must be disclosed. Apps may not store personal health information in iCloud. Guideline 5.1.2(vi) bars using Camera or Photo API depth and facial-mapping data for marketing.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Do not use CloudKit, iCloud Drive or NSUbiquitous storage for wound photos or records; keep them on the backend. Never use health data for marketing, including TetraSol product promotions, without separate permission. Whether ordinary iCloud device backups count as 'storing in iCloud' is not stated, so consider marking cached PHI files isExcludedFromBackup and keeping them in SecureStore or encrypted storage.
- **[verified-official]** Guideline 1.4.1: medical apps that could give inaccurate data, or be used to diagnose or treat patients, may get greater review scrutiny. Apps must disclose data and methodology behind accuracy claims and should remind users to check with a doctor before making medical decisions. If the app has regulatory clearance, a link to it should be submitted.  
  Source: https://developer.apple.com/app-store/review/guidelines/  
  Implication: Show 'consult a doctor' disclaimers on AI assistant answers and on wound guidance, plus emergency guidance. Make no diagnostic accuracy claims. Prepare App Review notes explaining the clinician roles and how they are verified.
- **[verified-official]** The privacy manifest is a file named PrivacyInfo.xcprivacy at the root of the iOS app bundle. Its top-level keys are NSPrivacyTracking (Boolean), NSPrivacyTrackingDomains (required when tracking is true), NSPrivacyCollectedDataTypes and NSPrivacyAccessedAPITypes. Every privacy manifest in the app must be valid, and App Store Connect rejects submissions containing invalid ones. TN3181 says that since November 12, 2024 a valid manifest has been required (error ITMS-91056 for invalid files). — effective 2024-11-12 (valid manifest, per TN3181)  
  Source: https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk  
  Implication: Ship an app-level manifest with NSPrivacyTracking=false and no tracking domains. Declare NSPrivacyCollectedDataTypes for what the app collects (see the data-types finding) and NSPrivacyAccessedAPITypes. Do not invent keys or values, because Xcode's privacy report breaks on custom values.
- **[verified-official]** Required Reason API declarations have been mandatory since May 1, 2024. App Store Connect does not accept apps that use a required reason API without an approved reason in the privacy manifest. Each executable or dynamic library bundle needs its own manifest. An SDK cannot rely on the app's manifest, and declared reasons must match the app's real functionality and must not be used for tracking. Fingerprinting is not allowed, regardless of ATT permission. — effective 2024-05-01  
  Source: https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api  
  Implication: Declare reasons for every required reason API used by app code and by statically linked pods. React Native 0.86 aggregation, described below, covers most pods automatically. Check the merged manifest in the prebuilt ios/ project before upload.
- **[verified-official]** NSPrivacyAccessedAPICategoryUserDefaults (UserDefaults) has four reasons. CA92.1: read and write information accessible only to the app itself. 1C8F.1: data shared within the same App Group. C56D.1: a third-party SDK wrapper used only when the app calls it. AC6B.1: the MDM managed-configuration or feedback keys.  
  Source: https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype  
  Implication: Declare UserDefaults with CA92.1. React Native core and expo-constants declare it, and so does the RN template. Add 1C8F.1 only if an App Group is added later, for example for a widget or notification extension.
- **[verified-official]** NSPrivacyAccessedAPICategoryFileTimestamp (creationDate, modificationDate, stat/fstat/lstat, getattrlist and related APIs) has four reasons. DDA9.1: display timestamps to the user, with no off-device use. C617.1: metadata of files inside the app container, app group container or the app's CloudKit container. 3B52.1: files the user explicitly granted access to, for example through a document picker. 0A2A.1: third-party SDK wrappers only.  
  Source: https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype  
  Implication: Declare FileTimestamp with C617.1; RN core declares it too. Add 3B52.1 only if wound documents are imported through a document picker and their metadata is read. A note for anyone reusing memory-based lists: 3B52.1, not 0A2A.1, is the reason for user-granted files.
- **[verified-official]** NSPrivacyAccessedAPICategorySystemBootTime (systemUptime, mach_absolute_time()) has three reasons. 35F9.1: measure time elapsed between in-app events or run timers; elapsed time may be sent off-device. 8FFB.1: calculate absolute timestamps for in-app events. 3D61.1: an optional bug report the user chooses to submit.

- **[verified-official]** Apple app name: 2 to 30 characters. Required and localizable (App Information). Editable only until you submit to App Review, then only when you create a new version.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/app-information  
  Implication: 'Dress My Wound' is 14 characters and 'غير لي' is 6, so both fit. Lock the names before the first submission, because changing them later needs a new version. Set the Arabic name in the Arabic localization under App Information.
- **[verified-official]** Apple subtitle: up to 30 characters. Optional and localizable. Must follow the metadata rules: no prices, no references to other apps, no unverifiable product claims.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/app-information  
  Implication: Write a separate English (U.K.) subtitle and Arabic subtitle, each 30 characters or fewer. Do not use clinical-efficacy claims such as 'heals wounds faster' (Guideline 2.3.7: unverifiable claims).
- **[verified-official]** Apple promotional text: up to 170 characters. Can be changed without submitting a new version.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information  
  Implication: Use this field for time-sensitive messages, such as TetraSol availability or tier launches, so the description stays stable. Still no prices or claims that cannot be verified.
- **[verified-official]** Apple description: up to 4000 characters, plain text only (no HTML). Required and localizable.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information  
  Implication: Write separate English and Arabic descriptions, each 4000 characters or fewer, with no markup. Guideline 2.3.2 requires the description to say clearly that Silver, Gold and Platinum need an additional purchase. Guideline 1.4.1 says to remind users to check with a doctor.
- **[verified-official]** Apple keywords: up to 100 bytes. Each keyword must be longer than two characters. Required and localizable. Do not repeat the app name or company name, and do not use other apps' or companies' names.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information  
  Implication: The limit is in bytes, not characters. Arabic letters take 2 bytes each in UTF-8, so the Arabic keyword set holds roughly 50 Arabic characters (this is an inference about encoding). Keep 'TetraSol', 'Dress My Wound' and 'غير لي' out of the keywords because the name and company are already indexed. Never use competitor names.
- **[verified-official]** Apple 'What's New in This Version': up to 4000 characters. Not available for the first version and required for every later version. Guideline 2.3.12 requires significant changes to be listed specifically.  
  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information  
  Implication: Prepare per-release notes in English and Arabic from version 1.0.1 onward. Generic text such as 'bug fixes' is only acceptable for minor releases.

  Source: https://developer.apple.com/help/app-store-connect/reference/app-information/platform-version-information

- **[verified-official]** Under Egypt's PDPL (Law 151/2020), health data (psychological, mental, physical or genetic) is SENSITIVE personal data. Children's data is always sensitive.  
  Source: https://portal.pdpc.gov.eg/faq  
  Implication: Treat all wound photos, wound and condition notes, AI-assistant health conversations, visit records and nurse/doctor clinical notes as sensitive data. Data from patients under 18 is sensitive whatever its type. Classify them in the data inventory and the record of processing.
- **[official-but-ambiguous]** The Executive Regulations of the PDPL are Minister of Communications and IT Decree No. 816 of 2025. The PDPC cites 'Executive Regulation No. 816 of 2025'.   Source: https://portal.pdpc.gov.eg/faq  
  Implication: The Executive Regulations are issued and in force, so compliance is mandatory now. The decree number is confirmed on the official PDPC site. The publication and effective dates come from a reproduction of the Gazette text (https://alhasswalawfirm.com/law-library/decree-816-2025), not from the Gazette itself.

  Source: https://www.bakermckenzie.com/en/insight/publications/2026/10/egypt-personal-data-protection-law-update  
  Implication: Any launch from now on falls after or within about two weeks of full enforcement. The company needs its PDPC license or permit, a registered DPO, a consent mechanism and records in place before go-live. Do not plan around a grace period.
- **[verified-official]** Data users must get a license or permit from the PDPC. A license lasts 3 years and a permit 1 year, both renewable.   Source: https://portal.pdpc.gov.eg/faq  
  Implication: The operating company needs a Controller (or Controller/Processor) license that covers sensitive health data.   Source: https://www.privacylaws.com/media/3263/egypt-data-protection-law-151-of-2020.pdf

## Critique (completeness & consistency review)

### contradictions
- Subscription sales channel on Android. apple-health-payments says 'a Silver/Gold/Platinum plan bought via Paymob on Android or web may be honored on iOS'. google-policy says SKUs that are mostly digital, or marketed as digital, must use Play Billing in Egypt: Play Billing is live there, steering is banned, and no alternative-billing program covers Egypt before at least 2027-09-30. Resolution: inside the Android app the tiers must be sold through Play Billing. Paymob for tiers is allowed only on the web. Google lets an app give access to content paid for elsewhere and does not require cross-platform parity (verified, answer/10281818). On iOS, 3.1.3(b) still requires the same tiers to be on sale as IAP.
- Where the real-world perks go in a mixed tier. apple-health-payments recommends one IAP subscription that includes the physical perks (priority matching, reduced platform fee). google-policy recommends selling only the digital/AI part through Play Billing and putting the real-world benefits into Paymob-priced visits. Both choices pull against Apple 3.1.3(e) and Play Payments §3, which forbid store billing for physical services. The two findings also classify 'priority matching' differently: google-policy calls it 'arguably digital', and apple-health-payments leaves it unresolved. One cross-store classification is needed, and neither recommendation has official confirmation.
- Paying for consultations is not symmetric across stores. Google exempts all regulated clinical services from Play Billing, whether live, remote or asynchronous. Apple exempts only real-time 1:1 services under 3.1.3(d), so asynchronous chat or AI-plus-clinician consults on iOS may need IAP. The google-policy implication ('remote consults can be charged through Paymob') must not be copied into the iOS payment classifier.
- Account deletion. apple-privacy says a link straight to a web deletion page is allowed. apple-health-payments says deletion 'must be started in-app'. Google requires both an in-app path and a public web deletion URL. Building both meets all three readings.
- 16 KB page-size timeline. The blog gave Nov 1, 2025, forum-quoted emails mention May 31, 2026, and the developer page blocks updates from Feb 1, 2027. The Play Console technical page says 'new app bundles uploaded ... must support them'. The finding's implication ('required now') and its 'official-but-ambiguous' rating conflict with the 'verified-official' rating of the Play Console finding.
- Inconsistent confidence for the same text. Guideline 5.1.3 (health data, no PHI in iCloud) is rated 'official-but-ambiguous' in apple-privacy and 'verified-official' in apple-health-payments.
- Apple's own sources contradict each other in three places. (a) The screenshot page header requires the medium-display Dynamic Island set, while the Face ID card falls back to the large-display set. (b) The iPhone Duo requirement is triggered by the 'iOS 27.1 SDK or later' on the spec page but by 'any apps or games submitted' in the news post. (c) Expo's SDK 54 changelog says predictive back would become the default in SDK 55/56, but the current docs still say 'Default to false'.
