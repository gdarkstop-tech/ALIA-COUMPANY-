# ADR 0017 — Production photo storage: private S3-compatible bucket, SSE-KMS, verified before use

- Status: accepted (2026-10-29) — adapter implemented and tested on an S3 emulator; **production NOT_CONFIGURED** (no approved bucket, contract or authorisation yet)
- Extends: [ADR 0015](0015-wound-intelligence-registry.md) (photo vault, signed links)
- Code: `apps/api/src/integrations/storage.ts` (`S3EncryptedStore`, activation rules), `apps/api/src/ops/storage-verify.ts`, `apps/api/src/ops/storage-cli.ts` (`storage:verify`, `storage:dev-bucket`), `infra/storage/*`, `scripts/ops/db-backup-restore-drill.sh`
- Tests: `apps/api/test/storage.test.ts`

## Context
ADR 0015 kept production photo storage `NOT_CONFIGURED`: only a development adapter writing
encrypted files to the API host existed. Production needs durable, private, encrypted storage with
backups and deletion that can be proven, without giving any client a storage URL, and without
switching on before the company has a provider contract and the privacy authorisations.

## Decision
1. **Adapter.** `S3EncryptedStore` (official AWS SDK v3, any S3-compatible provider):
   - objects are still encrypted by the API first (AES-256-GCM, object key bound as additional
     data), then written with **server-side encryption** — `aws:kms` with a customer-managed key
     by default (`S3_SSE`, `S3_KMS_KEY_ID`), or `AES256` / provider default where KMS headers are
     not supported;
   - `Cache-Control: no-store`, `application/octet-stream`, keys generated by the API only
     (`w/<uuid>.o|d`, `r/…`; anything else is refused before any request);
   - 3 attempts within a 20 s request timeout; failures become `ObjectStoreError`, rendered as
     `503 STORAGE_UNAVAILABLE` with the cause logged for operators and never sent to clients;
   - **no presigned or public URLs**: the API streams photos after the access check (ADR 0015).
2. **Activation (production).** The adapter is used only when endpoint (HTTPS — the server refuses
   to start otherwise), region, bucket, credentials, `OBJECT_STORAGE_KEY`, a KMS key (for SSE-KMS)
   **and `OBJECT_STORAGE_APPROVAL_REF`** are all present. Otherwise storage is `NOT_CONFIGURED` with
   the missing item as the reason; photo upload answers `NOT_CONFIGURED`. Development and tests use
   the adapter when `S3_*` points at a local emulator, else the encrypted local directory.
3. **Bucket configuration as code** (`infra/storage/`): public-access block, bucket-owner-enforced,
   default SSE-KMS with bucket key, versioning, lifecycle (non-current versions erased after
   30 days, incomplete uploads after 1 day, expired delete markers removed), a bucket policy denying
   non-TLS / TLS < 1.2 and writes without this KMS key, and a least-privilege API role
   (objects under `w/`, `r/`, canaries under `v/`, KMS only via S3).
4. **Verification before use.** `storage:verify` writes a synthetic canary and passes only if:
   HTTPS; bucket reachable; versioning on; lifecycle ≤ 35 days; SSE (and the KMS key) reported on the
   object; ciphertext at rest; **anonymous object read and listing refused**; ciphertext moved to
   another key fails its integrity check; delete → restore from the previous version works; every
   canary version removed. Its output is kept with the approval reference.
5. **Retention and deletion.** Deleting a photo removes the row immediately and purges the object
   (delete marker); earlier versions — the backup — are erased by the lifecycle rule within 30 days.
   Database backups: encrypted (age) dumps / provider PITR ≤ 30 days; restore drill script.

## Evidence (2026-10-29, development container)
- Unit and API tests (always run): activation matrix, SSE/no-store/ciphertext on the wire, error
  mapping (`INTEGRITY`, `NOT_FOUND`, `PROVIDER`), invalid keys never sent, 503 without leaking the
  cause.
- **S3 emulator** (moto 5.2.5 server with IAM signature enforcement — not a cloud provider): full API
  flow (consented internal-test upload → two encrypted objects → signed-link read → delete → purge →
  delete marker → link refused) and `storage:verify` → **VERIFIED**. Negative control: the same
  verifier against the emulator without authentication → **FAILED** on "anonymous access refused".
  The emulator accepts SSE-KMS headers without a real KMS; real KMS behaviour is verified only when
  `storage:verify` runs against the company's bucket.
- Database restore drill: backup 928 KB encrypted, no plaintext; restore 9.2 s; 95 tables /
  9 424 rows, RLS flags, 150 policies, 213 functions and 27 migrations identical; RLS enforced in
  the copy; total 15.5 s (development data).

## Consequences
- Production photos can be switched on by configuration once the company supplies the bucket,
  credentials, keys and approvals — no code change.
- Two independent encryption layers (API key from the secret manager + provider KMS); a storage
  provider breach alone does not reveal photos.
- Deletion is immediate in the product and complete in backups within 30 days.

## Rejected alternatives
- *Presigned bucket URLs for viewing* — cannot be revoked once issued and bypass per-view audit.
- *Treating the emulator run as production verification* — only the company's bucket can be verified.
- *Hard-deleting every version on each purge* — would remove the only protection against operator
  error; the 30-day lifecycle is the documented compromise.
